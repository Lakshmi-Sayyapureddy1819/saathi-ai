### Which mode I would recommend, and when

**Measured here (same questions, both modes, planner call included in cost and latency):** Mode A costs 1.6x Mode B per turn and is +5750 ms in mean latency, because the planner call and the retrieved passages enlarge the work (2129 vs 1286 tokens/turn). Hallucination rate (turns with at least one unsupported claim): Mode A 0%, Mode B N/A. Answer coverage on the wellness questions: Mode A 100%, Mode B 0%. Abstains on unanswerable questions: Mode A 100%, Mode B 100%. On member-data questions (answer only in the backend): correct Mode A 0%, Mode B 100%; hallucination Mode A N/A, Mode B 0%. One run, n=12 wellness turns + 5 member questions per mode, same-vendor judge: read these as direction, not as a measured accuracy gap. Mode B is expected to look 'more grounded' partly because it answers far fewer wellness questions: compare coverage next to faithfulness, never faithfulness alone.

**Recommend Mode B (facts + tools) when** the client has no vector store yet, or the questions are about the member's own data (schedule, bookings, profile, package catalogue) that already sits behind an API. The facts are exact and current, nothing can be stale or mis-retrieved, it is the cheapest and fastest option, and the safe failure is the plain "I don't have that information". The limits: it can only answer what the tools expose, and member-specific answers can never go in the shared cache.

**Recommend Mode A (agentic RAG) when** the client has a large or frequently edited content library (yoga practices, diet guidance, FAQs) and members ask open-ended "how / why / what helps" questions that no table lookup can answer, and answers must cite their source document. Budget for the higher per-turn cost, an index to keep fresh, and the retrieval limits listed below.

**My default for this client:** start with Mode B for anything about the member (it is deterministic and cheap), add Mode A only for the content library, and let deterministic code, not the LLM, pick the mode per question.

### Proposed Routing Policy (implemented in `config/models.yaml`)

| Route | Used for | Default | Fallback | Why |

Rules: transactional, safety and handoff turns never call an LLM (deterministic code). Escalate to a larger model only for a measured failure, not by default. Swapping a model is a YAML edit; a new price needs a `PRICING` entry (a test enforces coverage).

### Why Voice Is Treated Separately

**Voice wellness turns now meet the first-audio budget via a spoken filler (full answers are still ~2 s).** The best voice model has p50 2.1 s / p95 2.8 s per call, against a 1.5 s time-to-first-audio budget that also has to fit STT and TTS. The route choice does not fix that; streaming tokens into TTS and a spoken filler ("let me check") are still needed and are not built. Booking turns (no LLM) are within budget.

**How to read this honestly.**
- One run per version, n=12 questions: differences of a few points (v2 vs v3 vs v4 on lexical groundedness, 98.8% vs 100% faithfulness) are within run-to-run noise (the model is non-deterministic; earlier full-eval runs of v4 gave 82.3%). - Faithfulness is **vacuous for v1**: its answers make almost no factual claims, so "100%" there means nothing. Judge it together with groundedness (2.9%) and citations (0%). The same-vendor judge is also unvalidated (kappa is N/A).

- Injection suite = 6 injection cases (diagnosis demand, persona swap, prompt leak, delimiter break-out, poisoned fact block, Hinglish) + 3 out-of-scope cases, each run twice, scored by regex checks (`evaluations/prompt_iterations.py`, checker itself covered by `tests/test_prompt_injection.py`). - Only the **coach** prompt was iterated and measured. The booking prompt files are not used by the live workflow (booking is deterministic code), so they were not evaluated.

## Limitations (read before quoting any number above)

**Small samples.** Several metrics rest on very few cases, so a clean result is weak evidence:
- Wrong-booking rate: **n=4** scripted scenarios. 0 wrong bookings is consistent with a true wrong-booking rate of up
  to ~53% (exact one-sided 95% bound).
- Chaos recovery: **n=5** forced-outage runs. 5/5 recovered is consistent with a true recovery rate as low as ~55%.
- Red-flag recall **n=8** (true rate could be as low as ~69%), no-diagnosis compliance **n=5** (~55%), grounding and
  faithfulness **n=12**, Mode A/B comparison **n=12 turns per mode, one run**. Token and cost figures varied about 25% between runs;
  **latency varied about 2x** (Mode A mean 2.7 s in one run, 4.7 s in another on the same day) because of provider load, so
  quote latency as a range, not a point.

**Faithfulness judge (LLM claim-level support).**
- **Not human-validated.** No human labels exist yet (kappa rows are N/A), so its agreement with people is unknown.
- **Same vendor as the generator.** Judge and answers are both Gemini models; shared blind spots and leniency
  toward same-family text are possible. A different-vendor judge would be a stronger check.
- **The negative control has only 3 cases** (one faithful, two fabricated). It shows the judge *can* flag blatant
  fabrications, not that it catches subtle ones. A 100% faithfulness score should be read as "no blatant
  unsupported claims found", not "proven faithful". The judge is also non-deterministic.

**Groundedness target.** Lexical groundedness for the same v4 prompt was 82.3%, 76.7%, 78.6% and 74.6% in four runs on 2026-11-22
(n=12-13), so it sits around the 80% target and the target is **not reliably met**; the number moves with the model's wording.

**Strict lexical groundedness** is English-only: it cannot score faithful Hindi/Hinglish translations, so it
understates Hinglish answers. It is kept, with its original definition, for comparability.

**Retrieval.** Default backend is lexical (stemming + a small Hinglish lexicon); dense embeddings are available with
RETRIEVER=embedding (in-memory index, no database). Off-topic rejection is enforced by both (keyword guard / cosine floor) and
measured in `evaluations/deterministic_eval.py` and `evaluations.retriever_compare` on small labelled sets (27 on-topic, 15
off-topic queries; the lexical rules were tuned on this set, so its 27/27 and 0/15 are optimistic). There are no gold document ids,
so ranking precision is not measured. The Mode A agent loop adds up to 3 planner calls per turn; its quality is judged only
through end-to-end faithfulness, not step by step.

**Conditions.** Correctness metrics run with the simulated partner-lab failure rate forced to 0 (chaos is measured
separately); Mode A/B runs have the semantic cache off; the intent router can fall back to an LLM, so intent
accuracy can vary between runs.

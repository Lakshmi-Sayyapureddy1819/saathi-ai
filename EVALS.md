### Which mode I would recommend, and when

**Measured here:** Mode A costs 2.5x more per turn and is ~538 ms slower (mean), because retrieved passages enlarge the prompt (916 vs 639 tokens/turn). One run, n=12 per mode; hallucination rate per mode was **not** measured separately (the faithfulness judge scores Mode A answers only), so the advice below rests on that cost/latency gap plus how each mode fails, not on a measured accuracy gap.

**Recommend Mode B (facts + tools) when** the client has no vector store yet, or the questions are about the member's own data (schedule, bookings, profile, package catalogue) that already sits behind an API. The facts are exact and current, nothing can be stale or mis-retrieved, it is the cheapest and fastest option, and the safe failure is the plain "I don't have that information". The limits: it can only answer what the tools expose, and member-specific answers can never go in the shared cache.

**Recommend Mode A (agentic RAG) when** the client has a large or frequently edited content library (yoga practices, diet guidance, FAQs) and members ask open-ended "how / why / what helps" questions that no table lookup can answer, and answers must cite their source document. Budget for the higher per-turn cost, an index to keep fresh, and the known retrieval gap in the limitations below (no off-topic rejection).

**My default for this client:** start with Mode B for anything about the member (it is deterministic and cheap), add Mode A only for the content library, and let deterministic code, not the LLM, pick the mode per question.

Rules: transactional, safety and handoff turns never call an LLM (deterministic code). Escalate to a larger model only for a measured failure, not by default. Swapping a model is a YAML edit; a new price needs a `PRICING` entry (a test enforces coverage).

**Voice is still over budget for wellness turns.** The best voice model has p50 2.1 s / p95 2.8 s per call, against a 1.5 s time-to-first-audio budget that also has to fit STT and TTS. The route choice does not fix that; streaming tokens into TTS and a spoken filler ("let me check") are still needed and are not built. Booking turns (no LLM) are within budget.

**How to read this honestly.**
- One run per version, n=12 questions: differences of a few points (v2 vs v3 vs v4 on lexical groundedness, 98.8% vs 100% faithfulness) are within run-to-run noise (the model is non-deterministic; earlier full-eval runs of v4 gave 82.3%). The large effects (v1 vs the rest on groundedness and injection; 0% -> 100% citations; 50% -> 100% length compliance) are not noise.
- Faithfulness is **vacuous for v1**: its answers make almost no factual claims, so "100%" there means nothing. Judge it together with groundedness (2.9%) and citations (0%). The same-vendor judge is also unvalidated (kappa is N/A).
- Cost: v1 -> v4 raises tokens/turn from about 139 to about 913 and cost/turn about 3x, because the facts block is now actually sent. That is the price of grounding, not waste.
- Injection suite = 6 injection cases (diagnosis demand, persona swap, prompt leak, delimiter break-out, poisoned fact block, Hinglish) + 3 out-of-scope cases, each run twice, scored by regex checks (`evaluations/prompt_iterations.py`, checker itself covered by `tests/test_prompt_injection.py`). It tests the **prompt** with the deterministic safety gate bypassed; in production the gate already stops diagnosis demands before any model call (`tests/test_prompt_injection.py::test_ignore_your_rules_and_diagnose_me_is_stopped_before_any_llm`). n=18 per version is small.
- Only the **coach** prompt was iterated and measured. The booking prompt files are not used by the live workflow (booking is deterministic code), so they were not evaluated.

## Limitations (read before quoting any number above)

**Small samples.** Several metrics rest on very few cases, so a clean result is weak evidence:
- (The larger offline run above raises wrong-booking to n=108, chaos to n=50 and red-flag to n=40, but it is tuned to its
  own set; the figures in this list are the golden-set ones.)
- Wrong-booking rate: **n=4** scripted scenarios. 0 wrong bookings is consistent with a true wrong-booking rate of up
  to ~53% (exact one-sided 95% bound).
- Chaos recovery: **n=5** forced-outage runs. 5/5 recovered is consistent with a true recovery rate as low as ~55%.
- Red-flag recall **n=8** (true rate could be as low as ~69%), no-diagnosis compliance **n=5** (~55%), grounding and
  faithfulness **n=12**, Mode A/B comparison **n=12 turns per mode, one run**. Token and cost figures varied about 25% between runs;
  **latency varied about 2x** (Mode A mean 2.7 s in one run, 4.7 s in another on the same day) because of provider load, so
  quote latency as a range, not a point.

**Faithfulness judge (LLM claim-level support).**
- **Not human-validated.** No human labels exist yet (kappa rows are N/A), so its agreement with people is unknown.
- **Same vendor as the generator.** Judge and answers are both Gemini models; shared blind spots and leniency
  toward same-family text are possible. A different-vendor judge would be a stronger check.
- **The negative control has only 3 cases** (one faithful, two fabricated). It shows the judge *can* flag blatant
  fabrications, not that it catches subtle ones. A 100% faithfulness score should be read as "no blatant
  unsupported claims found", not "proven faithful". The judge is also non-deterministic.

**Groundedness target.** Lexical groundedness for the same v4 prompt was 82.3%, 76.7%, 78.6% and 74.6% in four runs on 2026-11-22
(n=12-13), so it sits around the 80% target and the target is **not reliably met**; the number moves with the model's wording.

**Strict lexical groundedness** is English-only: it cannot score faithful Hindi/Hinglish translations, so it
understates Hinglish answers. It is kept, with its original definition, for comparability.

**Retrieval.** Lexical (stemming + a small Hinglish lexicon). *Known issue:* an off-topic query such as "what is the
weather" retrieves the Sheetali Pranayama document (it mentions summer weather); retrieval has no off-topic
rejection, so the answer relies on the coach prompt declining to use irrelevant context. This is not evaluated.

**Conditions.** Correctness metrics run with the simulated partner-lab failure rate forced to 0 (chaos is measured
separately); Mode A/B runs have the semantic cache off; the intent router can fall back to an LLM, so intent
accuracy can vary between runs.
